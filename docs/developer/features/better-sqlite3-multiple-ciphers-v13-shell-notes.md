# quilltap-shell and better-sqlite3-multiple-ciphers 13 — what changes, and when

**Audience:** whoever writes the quilltap-shell spec. This is a description, not the spec. **Written:** 2026-10-28, against shell `4.2.4` (Electron 41.10.7, Node 24.18.0, N-API 10) and server `4.12.0-dev`. Server-side spec of record: [complete/better-sqlite3-multiple-ciphers-v13.md](complete/better-sqlite3-multiple-ciphers-v13.md) (implemented 2026-10-28). This file is kept in the server repo only because that is where the research happened; move or copy it into the shell repo as you see fit.

## The short version

1. **No shell release is required for server 4.12 to work.** The shell force-copies its own driver (`node_modules/better-sqlite3`, the v12 build compiled against Electron's ABI) over whatever the extracted server tarball has — the tarball strips the module anyway — so a 4.12 server under shell 4.2.4 runs on v12. That is verified safe: the server's code uses no v13-only API (and the server repo now carries a rule not to until the shell ships v13), and databases written by either driver open in the other.
2. **There is no compatibility gate, in either direction.** User decision 2026-10-28. Do not add a capability flag, a health-status branch, a `.dbkey` field, or a version refusal for this. The existing `QUILLTAP_SHELL` / `QUILLTAP_SHELL_CAPABILITIES` contract is unchanged.
3. **The shell will still have to move to v13 at its next release, for a mechanical reason:** `scripts/check-server-alignment.ts` runs at the head of every local `electron:build:*` and compares the shell's installed driver against the range in the server repo's `package.json`. The moment the server declares `^13.0.3`, a local shell build fails that guard. (CI calls `rebuild-native-modules.ts` directly and never runs the guard, so a CI-only release would still ship v12 and still work — but silently out of alignment.) So: bump when you next cut a shell release for any reason; no urgency, no coupling to a server version, no "4.3" significance — a patch bump is fine.
4. **When you do bump, the Electron compile step goes away entirely.** v13 is a Node-API addon with the prebuilt binary for every supported platform inside the npm tarball. The published `darwin-arm64` prebuild loads under the shell's Electron 41 (`ELECTRON_RUN_AS_NODE`, ABI 145) exactly as it does under plain Node 24, with no `node-gyp`, no Electron headers, no `--dist-url`. The 4.1.5–4.1.11 failure class (a plain-Node binary gatecrashing an Electron build) cannot recur, because there is no longer a per-ABI binary to get wrong.

## What v13 is, mechanically

- Package: `better-sqlite3-multiple-ciphers@13.0.3` (2026-08-07). better-sqlite3 13.0.3, SQLite 3.53.4, SQLite3MultipleCiphers 2.4.0. `engines.node >= 22`. Sole dependency `node-addon-api@^8` (build-time headers; nothing in `lib/` requires it at runtime). `gypfile: false`; **no `install` script**; `prebuild-install` and `bindings` are gone.
- Layout: `lib/index.js` → `lib/binding.js#getBinding()` → `prebuilds/<platform>-<arch>.node`, with `linuxmusl-*` chosen when `process.report.getReport().header.glibcVersionRuntime` is absent; falls back to `build/Debug|Release/better_sqlite3.node` only if no prebuild matches. Eight prebuilds ship: `darwin|linux|linuxmusl|win32` × `x64|arm64`.
- The `exports` map exposes `.`, `./<platform>-<arch>` (a direct per-platform entry that skips detection), and `./package.json`. Subpath requires such as `…/lib/binding.js` throw `ERR_PACKAGE_PATH_NOT_EXPORTED` unless done by absolute filesystem path.
- Requirements: Electron ≥ 35 (shell is on 41); Linux glibc ≥ 2.35; x86 Windows and armv7 Linux discontinued.
- Size: 34.4 MB unpacked, of which ~22 MB is binaries for other platforms and ~10 MB is `deps/sqlite3/sqlite3.c`. The maintainer's release note explicitly asks packagers to keep only the target platform's binary.

Verified on 2026-10-28 (macOS arm64): load + encrypted round trip under Node 24.13.1 and under Electron 41.10.7; an encrypted WAL database with FTS5 written by v12 read and written by v13 and reopened by v12, and the reverse, `quick_check` ok both ways. The server's only `rekey` runs in `journal_mode = DELETE`, so the one behavioural change in SQLite3MultipleCiphers 2.4.0 (rekey allowed in WAL) is irrelevant.

## Things worth knowing before writing the spec

- **Linux users gain headroom, not lose it.** The shipped v12 binary was compiled on `ubuntu-latest` (24.04, glibc 2.39), so the AppImage/deb almost certainly already required a glibc newer than 2.35 (a binary links the versioned symbols of the host it was built on). v13's prebuild floor is glibc 2.35 (Ubuntu 22.04 / Debian 12). Mention it in the Linux release notes once; it is not a regression.
- **`process.report` on Linux.** The loader's musl test calls `process.report.getReport()`. It exists in Electron's Node; the Step 3 probe under Electron on the Linux runner is what proves it. Keep that probe in CI for all three platforms.
- **Dev mode gets simpler.** `electron:dev` already runs against the repo's `node_modules`; with v13 the copy npm installs is the one Electron can load, so no pre-step is needed for local development.
- **Future Electron bumps stop waiting on the fork.** The Electron 42 blocker chronicled in the 4.1.5 changelog (a V8 `ExternalPointerTypeTag` change the fork had not picked up) was a consequence of the old V8-coupled addon. A Node-API addon is insulated from V8 internals; Electron's N-API version (10 on 41) is the only contract.
- **Docker mode is unaffected**: the image carries its own driver (pruned to one architecture by the server spec). Remote mode never touched a driver.
- **What a user sees when it goes wrong.** The server now logs the driver version and SQLite version at boot (info level); in `embedded-server.log` that is the line to look for — under a 4.2.x shell it will say `12.11.1 / 3.53.2`, under a v13 shell `13.0.3 / 3.53.4`. Both are fine; the line exists so that support threads stop guessing which binary ran.

## Suggested acceptance for the shell spec

1. `npm ci` on the shell produces no compiler output; `node_modules/better-sqlite3/prebuilds/` holds eight files before the select script runs and one after.
2. The Electron probe passes on mac, win and linux runners and prints `chacha20` and `3.53.4`.
3. The packaged app's `app.asar.unpacked/node_modules/better-sqlite3/prebuilds/` contains exactly the target binary.
4. A fresh standalone cache (delete it first) + embedded boot against a scratch instance: the server reaches `healthy`, the new boot line in `embedded-server.log` reads `13.0.3` / `3.53.4`, and the cache's `node_modules/better-sqlite3/prebuilds/` has the one file.
5. The same embedded boot against an instance last opened by a 4.2.x shell (v12) opens without complaint — that is the interoperability the server verified, exercised through the shell's own path.
6. `npm run electron:build:mac:dev` passes `check-server-alignment` with the server repo on `^13.0.3`.
