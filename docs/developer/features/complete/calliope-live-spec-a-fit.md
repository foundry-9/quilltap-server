# Calliope Live — Spec A fit report (Stage 2.5)

**Status:** findings, 2026-11-14. Stage 2.5 of
[calliope-live-spec-a-token-registry.md](calliope-live-spec-a-token-registry.md).
This tests the semantic tier that Stage 2 added against the six bundled
themes' actual values. The point is to keep the design from fitting only the
default theme.

The tables at the end are generated by `scripts/theme-fit-report.ts`; rerun it
after changing a family. Everything above them is written by hand.

## Method

- **Values.** A theme's values are its resolved snapshot (the Stage 0
  fixtures), in light and dark. A theme *sets* a variable when it declares it
  (the audit CSV). Only values a theme sets are counted, because what a theme
  leaves alone is the default anyway.
- **Anchoring.** Bundled themes have no semantic tokens yet. Each one is read
  off the theme's own component values, from the first component whose
  registry formula can be inverted:
  - `var(S)` gives S directly.
  - `color-mix(in srgb, var(S) <p>, transparent)` gives S as that colour made
    opaque and, when the share is `var(T)`, T as its alpha.
  - Components whose share is a token are read first.
  - A token no component inverts takes a stated anchor: the hover shade is
    `black`, the hover tint and the Staff accent are the theme's page text and
    muted colour.
- **Evaluation.** Each component the theme sets is evaluated from the
  **registry's actual formula**, with the anchored semantic values and the
  theme's own values for anything else the formula reads. The result is
  compared with what the theme renders:
  - **exact:** renders alike, meaning the same 8-bit RGBA and the same text;
  - **near:** ΔE in OKLab ≤ 0.02 (about a just-noticeable difference), with
    both colours composited over the theme's background in that mode;
  - **override:** still needs a component value.
- **Alternatives.** Where the registry departs from the derivation the spec
  first proposed, that derivation is measured too, so the choice can be seen.
- **The 2.3 features.** These live in rules, not variables. They are measured
  on the themes' hand-written `styles.css`: of the declarations a theme writes
  for a feature, how many the new tokens can express.

Every Stage 2 derivation leaves the default theme exactly as it was: the
snapshot shows 0 changed values in all fourteen fixtures. In-browser probes of
5,278 computed properties per run, covering headings, buttons, a dialog,
inputs, a card, `::selection`, the root and the shell, also showed no change
in any theme or mode.

## The families

### Category palette (`--qt-badge-*`)

**Tokens.** 17 categories, each a colour and a foreground
(`--theme-category-<id>` / `-foreground`), plus `--theme-category-tint`
(12% light, 25% dark).

**Derivation.**
- Badge background: `color-mix(in srgb, var(--theme-category-<id>) var(--theme-category-tint), transparent)`.
- Badge text: `var(--theme-category-<id>-foreground)`.
- The capability badge keeps its own shares (8% / 18%), as it always has.

**How the categories were chosen.** Badges whose background and text are
identical in all fourteen theme/mode pairs share a category:
- `manual` and `source-included` share `user-character`;
- `enabled` shares `chat`;
- every other badge has its own.

The spec's "one colour per entity category" became a colour *and* a
foreground. In every theme a badge's text is a different, darker or lighter,
colour from its tint base: 8–18.5 lightness points apart in the default theme,
and no single offset fits.

**Fit.** 95% (275 exact, 42 near, 15 override).
- The overrides are themes whose tint is not the same for every category. In
  art-deco and great-estate, `message` and `project` sit at 0.12 where
  `character` is at 0.15, and the dark strengths vary between 0.2 and 0.3. The
  tint is anchored from `character`, so those categories miss.
- The one-colour alternative, where text is the category colour, reproduces
  64%, with the text values accounting for most of the misses.

### Status (`--qt-alert-*`)

**Tokens.** One alert colour and one foreground per status
(`--theme-status-success`, `-warning`, `-danger`, `-info`, each with
`-foreground`), plus a fill strength (`--theme-status-tint`, 8% / 15%) and an
edge strength (`--theme-status-edge`, 25% / 40%).

**Derivation.**
- Background: the status colour at the fill strength.
- Border: the same colour at the edge strength.
- Text: the status foreground.

**Fit.** 100% (140 exact, 4 near).
- Every theme draws an alert's background and border from one colour at two
  strengths that it applies to all four statuses. The exception is warning,
  which is a little stronger in art-deco and great-estate, hence the 4 near.

**The alternative.** The spec's own suggestion was to take the alert colour
from the action colours (`--theme-success` and friends). It reproduces 64%.
- In no theme, the default included, is the alert colour the action colour;
  alerts are lighter.
- So the status palette is its own semantic family. The solid status badges
  (`--qt-status-*`) already derive from the action colours and are left alone.

### Chat surfaces (`--qt-chat-*`)

**Tokens.**
- `--theme-chat-assistant` / `-foreground` (defaulting to the theme's muted
  colour and page text).
- `--theme-chat-system` / `-foreground` (the Staff bar).
- An accent and a label colour for each special message kind:
  `--theme-chat-whisper`, `-silent` and `-wardrobe`, each with `-foreground`.
- The user bubble already had semantic tokens (`--theme-chat-user`).

**Derivation.** This is the shape the default theme already used, now named:
- A kind's background is the assistant surface mixed with the kind's accent
  (60/40, 65/35 and 60/40 for whisper, silent and wardrobe).
- Its border is the accent.
- Its label is the kind's foreground.

**Fit.** 84% (86 exact, 12 near, 18 override).
- All 18 overrides are kind backgrounds. Four themes use the same mix at a
  different share (35–45%); earl-grey and rains write a literal background.

### Roleplay text (`--qt-rp-*`, `--qt-roleplay-*`)

**Tokens.**
- A surface and a text colour for each annotation (dialogue, narration, inner
  monologue, out of character).
- A colour and a foreground for each of the four template chips.

**Derivation.** One to one: each component reads its own semantic token. The
fit is therefore 100% by construction, and it says nothing about derivation.

**Reading.** The family names a palette; it does not derive one.
- Across the six themes the annotation colours have no shared relationship to
  the page colours. Of the four themes that set dialogue text, two match the
  page text.
- The family should stay one to one. The insert buttons (`--qt-rp-button-*`)
  were left as component tokens: their colours relate to nothing else, in any
  theme.

### Terminal (`--qt-terminal-*`)

**Tokens.** Background, text, cursor, selection and the sixteen ANSI colours,
as a named block (`--theme-terminal-*`).

**Derivation.** One to one; 100% by construction, as the spec expected
("already primitives in effect"). The terminal chrome still derives from the
terminal background and text.

### Overlay (`--qt-overlay-*`, `--qt-dialog-backdrop`)

**Tokens.** `--theme-scrim`, `--theme-scrim-strength` (85%) and
`--theme-scrim-foreground`.

**Derivation.**
- Every overlay surface is the scrim colour at a share: the full overlay at
  the strength, the medium and light overlays, the caption and the dialog
  backdrop at fixed shares.
- The glass buttons are the scrim foreground at 10% / 20%.

**Fit.** 64% (41 exact, 26 near, 37 override). The overrides fall in two
places:
- **Dialog backdrop** (10): themes use 0.5–0.55 where the default is 0.45.
- **Glass buttons** (19): five of the six themes tint them with their accent
  colour (gold, amber), not the text colour.

A separate accent token for the glass buttons would recover most of the
button overrides. That is a small follow-up, worth doing if an editor exposes
the family.

### Interaction states (hover)

**Tokens.**
- `--theme-hover-shade` (black): what a solid fill mixes toward.
- `--theme-hover-tint` (the page text): what a quiet surface takes a little
  of.
- Each component keeps its own share (80–88%).

**Fit.** 46% (0 exact, 32 near, 38 override). The alternative (one share for
every solid fill, read from the theme's success-button hover) does worse, at
15%.

**Reading.** This family is about the half the spec names as its threshold,
and it does not derive well. Hover colours in the bundled themes are design
decisions, not a mixing rule:
- art-deco's primary hover turns gold;
- great-estate's is a gradient;
- earl-grey and rains write literal colours;
- madmans-box lightens instead of darkening.

**Recommendation.** Hover colours stay literal at the component tier. The two
tokens are worth keeping only as a convenience: a dark theme can flip
`--theme-hover-shade` to white once instead of on every button. An editor
should present them that way, not as a family that drives the hovers. No
active-state rule was added: no existing active value in any theme, the
default included, is a mix, so there is nothing to derive.

## The 2.3 features

Each feature has app-owned rules. They sit in `@layer base` or
`@layer components`, or behind an attribute where no default value can be a
no-op, so a version 1 theme's own unlayered rule still wins.

| Feature | Tokens | App rule and default behaviour | Declarations expressible |
|---|---|---|---|
| Text selection | `--qt-selection-bg`, `-fg` | `::selection` in `@layer base`; the defaults are the default theme's values, which replace its old `[data-theme="default"] ::selection` rule | 100% |
| Scrollbar | `--qt-scrollbar-width` (auto), `-thumb` and `-track` (optional), `-thumb-hover` (optional), `-size`, `-radius` | `scrollbar-width` / `scrollbar-color` on `:root` in `@layer base`; unset thumb and track leave `auto`. WebKit rules sit behind `data-qt-scrollbar`, because any `::-webkit-scrollbar` rule switches Safari to custom scrollbars | 93% |
| Focus ring | `--theme-focus-ring-width` / `-offset` (existing), `--qt-focus-ring-color`, `--qt-focus-ring-glow` | `:focus-visible` behind `data-qt-focus-ring`; no outline value is a no-op against the browser's own ring | 100% |
| Headings | `--qt-heading-font` (existing); `--qt-heading-font-weight`, `-letter-spacing`, `-text-transform`, `-color` (optional) | Read by `.qt-heading-*`; unset, each level keeps its own value | 93% (the themes target bare `h1`–`h3`, which these classes do not cover) |
| Button text | `--qt-button-letter-spacing`, `-text-transform` (optional) | Read by `.qt-button` and its variants; unset is `revert-layer`, keeping a `<button>`'s browser default and a link's inherited value | 71% |
| Form control radius | `--qt-input-radius` (existing) | `.qt-input`, `.qt-textarea` and `.qt-select` already shared it; nothing added | 100% |
| Card and dialog border | `--qt-card-border`, `--qt-dialog-border` (existing), `--qt-dialog-border-width` (1px) | `.qt-dialog` reads the width | 100% |
| Colour scheme | `--qt-color-scheme` (`normal`) | `color-scheme` on `:root` in `@layer base` | 100% |
| Page background | `--qt-page-background-image` (`none`), `-size`, `-position`, `-attachment`, `-repeat` | Behind `data-qt-page-background`: the image on `body` and eight page surfaces transparent, unless a story background is showing. The themes' "undo" rules are not needed: the app rule applies under `:not(:has(…))` | 84% |

`applyThemeToDom` takes the three switches (`pageBackground`, `focusRing`,
`scrollbar`). A version 1 theme passes none. Stage 3 sets them for a version 2
theme from its tokens.

**Root baseline.** The default theme's root baseline (font smoothing,
`text-rendering`, smooth scrolling, thin scrollbar) stays scoped to
`[data-theme="default"]`. All six bundles set smoothing, smooth scrolling and
a thin scrollbar, but none sets `text-rendering` or `-moz-osx-font-smoothing`,
so applying the baseline to every theme would change them.

## Density (2.4)

All 31 variables selected by the rule (all six themes set them, to one value
that differs from the default) take a `comfortable` value from the bundles.
`[data-theme][data-qt-density="comfortable"]` reproduces the bundles' shared
values exactly; the snapshot test checks this on the default theme in both
modes.

Three of the 31 are not really density: `--qt-button-transition` and
`--qt-card-transition` (150 → 200 ms) and `--qt-app-header-blur`. They are
included because the rule selects them and the audit grouped them with the
sizing constants. Spec C may want to move them to their own choice.

## Reading

**Families that derive well:**
- **status** (100%): one colour per status at two strengths, as every theme
  already does;
- **category** (95%): a colour and a foreground per category, one tint;
- **chat surfaces** (84%): accent mixes into the assistant surface;
- **overlay** (64%): above half, with the dialog backdrop and glass buttons as
  the known misses.

Two places where the spec's first idea was weaker than the shape the themes
actually use:
- Deriving alerts from the action colours reproduces 64%, against 100% for
  the status palette.
- One colour per category, with text derived from it, reproduces 64%,
  against 95% for a colour and a foreground.

**Families that do not derive:**
- **Roleplay and terminal** are named palettes, one to one. That is useful for
  an editor, but the 100% says nothing about derivation.
- **Interaction states** (46%) should stay literal per component, with the
  shade and tint offered as conveniences.
